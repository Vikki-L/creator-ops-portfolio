# 设计决策

[返回项目首页](../README.md) · [证据与缺口](evidence-and-gaps.md)

## 用两端视角解释同一条记录

A1 的 Coach 审核与 Creator 视频页、A2 的结算管理与 A6 Earnings，都在处理同一件协作事项。分端是为了让双方看到各自需要的信息与动作；项目说明应把这两端放在一起讲，避免把明细展示和算薪描述成互不相关的项目。

## 让 AI 结果能够被复核

A3 的重要设计是把判断拆成步骤，输出决策建议与理由，并将人工改判沉淀为 badcase。结构化输出有利于检查格式；格式正确不代表事实判断正确。仅在 Prompt 中写出 JSON / enum，也不等于运行时已经有 Schema 校验。

导入的旧材料对 AI 是否直接通过或拒绝有不同表述。统一案例按 AI 辅助、人工复核介绍；自动处理边界需以原始 PRD 和运行证据核实。只提供转录和元数据时，不能据此断言视频中的人物、产品出镜等视觉事实。

## 把算薪、确认和支付分开

A2 的公开设计采用系统生成明细、Creator 自助确认、CSV 批次处理的路径。它减少重复录入，同时保留异常处理和财务核对入口。CSV 导出仅表示文件已生成；支付完成需要支付结果支持。

旧文档中超期废弃、金额归零的表述作为历史设计保留，不能直接拿来当新系统默认规则。未确认、未支付和应付义务是不同概念，需回到实际合作条款及正式业务规则核对。

## 让监控与分析落到具体工作

B1 提供日常观察，B3 做周期评估；D1 影响模板和指导，D2 影响新人流程，D3 解释评分思路来源。这些材料的价值是展示数据怎样改变下一步工作，而不是展示看板数量。

约 30 条视频的判断属于旧业务中的经验假设。公开仓库未提供完整样本和验证过程，不能推广为预测任何 Creator 能力的通用阈值，也不能自动决定合作终止。

## 用历史问题决定自动化迭代

C1 的入职流程与 D2 的漏斗、FAQ 分析属于同一反馈循环。C2 的提醒、初审等功能也围绕既有协作环节展开。把它们单独拆成 Bot 作品容易丢失输入和下游；本次整理将它们放回服务的业务场景。

原文对 FAQ 的关键词匹配、LLM 聚类和后续智能回答有版本差异；分析时使用 LLM 不代表线上 Bot 已采用相同能力。
