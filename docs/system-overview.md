# 系统总览

## 项目边界

项目服务自营 UGC 团队：校园大使 Creator 持续生产内容，Coach 负责内容指导、审核与跟进，内部团队处理全局运营与结算。双端页面是协作入口；Bot、看板和分析是围绕这条业务链路的配套能力。

旧仓库包含不同阶段的工具与设计。整合它们的目的是说明同一业务系统的关系，不表示它们已经共享一个生产数据库，也不表示当前仓库提供了它们的运行代码。

## 角色

| 角色 | 核心工作 | 对应材料 |
|---|---|---|
| Creator | 投稿、读反馈、查看内容表现、确认收入 | A1、A6；模板库与个人概览在原总览中有提及 |
| Coach | 审核、指导、跟进所负责的 Creator | A1、B1、B3、C2 |
| 内部运营 / 管理 | 查看整体情况、维护业务规则、处理跨团队事项 | B1、B2、B3、B4；原总览提到 All Creators 与团队概览 |
| Onboarding 团队 | 身份确认、新人接入、入职异常 | C1、D2 |
| 财务 / 支付操作人员 | 核对结算批次、上传支付文件、确认结果 | A2，与 A6 共享确认进展 |

Coach 可见范围和内部管理权限需结合原始 PRD 验证；界面筛选本身不能替代后端权限控制。

## 三条需要连起来的链路

**内容链路**：B6 投稿入库 → A3 AI 辅助 → A1 Coach 复核与 Creator 反馈。AI 建议、人工结论和 Creator 看到的最终反馈应能区分。

**结算链路**：审核与视频记录 → A2 本周期明细 → A6 Creator 确认 / 异议 → 支付导出 → 结果核对。A2 与 A6 是同一结算流程的两个视角。

**培养链路**：B6 视频数据 → B1 日常监控 → B3 周期评分 → Coach 指导与管理动作。B2 / B4 / D1 为内容策略提供依据，D3 解释评分方法来源，D2 为 C1 的迭代提供依据。

## 共同业务对象

以下是对公开设计的概念归纳，**不是从生产数据库导出的字段规范**。

| 对象 | 为什么需要跨模块关联 | 应避免的混淆 |
|---|---|---|
| Creator 与 Coach 归属 | 入职、投稿、审核、监控都需要识别同一个人 | 换 Coach 后历史记录不应丢失 |
| 视频 / 投稿 | 审核、表现、模板统计、结算都围绕具体内容 | 同一链接重复投稿不应被当作多条有效产出 |
| 审核记录与反馈 | 双端读取同一次协作历史 | AI 建议、人工结论、修改后的版本不能互相覆盖 |
| 模板 | 内容指导、模板命中、表现分析需要统一引用 | 模板能力和某一次内容表现不是同一个对象 |
| 周期结算与明细 | Coach 算账与 Creator 确认应对应同一份明细 | 当前预估、已确认金额与已支付金额需要分开 |
| 数据快照与评分 | 看板和周期评估需要时间与样本口径 | 视频发布时长不同、样本不足时不宜直接比较 |

这些对象关系是整理后的设计说明；实际字段、权限与约束仍需以正式 PRD 为准。
